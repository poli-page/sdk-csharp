---
title: Retries and idempotency
description: How the SDK retries transient failures, and why a retried render can still store a second document.
---

The Poli Page .NET SDK retries transient failures automatically. Every POST carries an auto-generated `Idempotency-Key` (a lowercase UUID v4), the same on every attempt of one call. The API does not deduplicate on that key, so a retried render can store a second document (see [Idempotency](#idempotency)).

## Default retry policy

- Retried: HTTP 5xx (including `503 PUBLISH_IN_PROGRESS` and `504 RENDER_TIMEOUT`), HTTP 429 such as `RATE_LIMIT_EXCEEDED`, `network_error` and `timeout`.
- Never retried: `QUOTA_EXCEEDED` and `OVERAGE_CAP_EXCEEDED` (429) and `STORAGE_ACCESS_DENIED` (502), which waiting cannot fix: the quota lasts until the monthly reset and the bucket access until you restore it. `IsRetryable()` is `false` for them.
- Never retried: any other 4xx, a cancellation (`aborted`), and the presigned PDF download (`DOWNLOAD_FAILED`, whatever the storage status).
- A call makes at most `1 + MaxRetries` attempts (default `2`: three attempts); when they are exhausted, the last error is thrown.
- Delay before retry `n`: the failed answer's `Retry-After` header (integer seconds or an HTTP-date), clamped to 0–30 s and without jitter; otherwise `RetryDelay × 2^(n-1) × j`, with `j` uniform in `[0.5, 1.5)`. `Retry-After-Ms` is ignored. The wait is never shorter than the delay.
- `OnRetry` fires before each wait with the attempt about to start (`2` for the first retry), the delay and the reason. A cancellation during the wait throws `aborted` at once.
- `RequestTimeout` bounds each attempt, connection, headers and body together; each retry gets its own.

Every resend is one of these counted retries. The SDK makes sure the HTTP stack never sends a request again by itself (SocketsHttpHandler would otherwise resend a GET or DELETE whose connection closed before any answer): each attempt goes through `OnRequest` and counts against `MaxRetries`.

## Disabling retries

Set `MaxRetries = 0` to disable retries entirely:

```csharp
var client = new PoliPageClient(new PoliPageClientOptions
{
    ApiKey     = Environment.GetEnvironmentVariable("POLI_PAGE_API_KEY")!,
    MaxRetries = 0,
});
```

## Idempotency

Every POST includes an `Idempotency-Key` header, identical on every attempt of one call. GET, DELETE and the presigned download carry none.

The API does not deduplicate on `Idempotency-Key`: every `POST /v1/render` that reaches it stores a new document. A retry can therefore store a second document whenever the first attempt was stored but its answer was lost: a 5xx raised after the document was stored, a `timeout` that fired while the API was still rendering, or a `network_error` after the request reached the API (including an answer cut mid-body). A `503 PUBLISH_IN_PROGRESS` is raised before any render work, so retrying it never duplicates.

If a duplicate stored document matters to you, set `MaxRetries = 0` for renders and decide yourself whether to render again. You can still pass your own key, for example to correlate attempts in your logs:

```csharp
byte[] pdf = await client.Render.PdfAsync(
    new RenderInput
    {
        Project  = "billing",
        Template = "invoice",
        Data     = new Dictionary<string, object> { { "invoiceNumber", "INV-001" } },
    },
    new RequestOptions { IdempotencyKey = "invoice-INV-001-v1" });
```

## Example

```csharp
using PoliPage;

var client = new PoliPageClient(new PoliPageClientOptions
{
    ApiKey     = Environment.GetEnvironmentVariable("POLI_PAGE_API_KEY")!,
    MaxRetries = 4,
    RetryDelay = TimeSpan.FromMilliseconds(250),
    OnRetry    = evt => Console.WriteLine($"attempt {evt.Attempt} in {evt.Delay}: {evt.Reason}"),
});

byte[] pdf = await client.Render.PdfAsync(new RenderInput
{
    Project  = "billing",
    Template = "invoice",
    Data     = new Dictionary<string, object> { { "invoiceNumber", "INV-001" } },
});
```
